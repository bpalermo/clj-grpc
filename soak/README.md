# The switch ladder: what an existing REST service gains, one change at a time

The August campaigns established that gRPC streaming moves ~16× REST's
messages per core — measured with two different instruments, against REST
unary, so the gain could not be attributed to any one change. This harness
asks the narrower question a migration decision needs: **how much does each
switch a REST service could make actually buy**, with every adjacent pair of
arms differing in exactly one thing, on one instrument.

| rung | arm | what changed from the rung below | migration cost |
|---|---|---|---|
| 1 | `rest-h1` — Pedestal/Jetty, HTTP/1.1 only (`H2C=off`) | — | — |
| 2 | `rest-h2c` — the **same image on the same node**, h2c on (`H2C=on`) | transport | a config flag; clients must speak h2 |
| 3 | `grpc-jvm`, unary `SayHello` | protocol: JSON/Jetty → protobuf/Netty | clients and serialization change |
| 4 | `grpc-jvm`, bidi `Chat` stream | interaction model | the API contract changes |

Two payload tiers per rung: `tiny` (the August 16-byte body, byte-identical so
the new numbers can be checked against the old) and `realistic` (a nested
~1 KB message: 1,309 B as JSON, 1,025 B as protobuf — generated by
`//charts:bodies`, sizes recorded in `SIZES.txt`). `grpc-native` stays
deployed for the density/cold-start story but is not a rung.

All arms: identical 1-CPU/1 Gi Guaranteed pods, one arm per dedicated worker
(the REST pair shares worker-04 and runs one at a time — `rest-h2c` deploys
scaled to zero and `ladder.sh` flips the pair; the node has room for exactly
one Guaranteed arm), the load generator on its own worker. Deployments use
`Recreate`: a rolling surge pod cannot fit beside the old one on a pinned node. Server images are built by `.github/workflows/build.yaml` on
arm64 runners and pushed only when their manifest digest changes.

## One instrument: Nighthawk

Every rung is driven by [Envoy Nighthawk](https://github.com/envoyproxy/nighthawk)
from the `bpalermo/nighthawk` fork, which adds what upstream lacks: an arm64
image, gRPC unary (`--grpc-mode unary`), and bidi streaming with per-message
latency (`--grpc-mode bidi-stream`). k6 is gone from this harness — it cannot speak cleartext
HTTP/2 at all, and its closed-loop latency could not be reconciled with the
streaming driver's. Open loop throughout: Nighthawk never applies
backpressure, so a server past its knee shows up as `pool_overflow` (or
`stream_deferred`) and rising tails rather than as a client quietly slowing
down.

The stepped ramp is `charts/clj-grpc-soak/files/nighthawk/run.sh`: one
`nighthawk_client` invocation per step, each bracketed by a snapshot of the
arm's own `/metrics`. That endpoint is where CPU-per-request comes from —
**this cluster's Prometheus does not scrape cAdvisor** — so the arms report
their cgroup v2 `cpu.stat` and `memory.current` themselves. `run.sh` is also
the one place a mode turns into flags; the fork's flags are a one-file edit.

## Deploying

The chart (`charts/clj-grpc-soak`) is built by Bazel; image digests in
`values.yaml` are stamped at package time from the images the same graph
produced:

```sh
# from an arm64 host — it pushes what it builds
bazel run //charts:soak.install -- --namespace clj-grpc-soak --create-namespace
# or the CI-published chart, from anywhere
helm install clj-grpc-soak oci://ghcr.io/bpalermo/clj-grpc/charts/clj-grpc-soak \
  --namespace clj-grpc-soak --create-namespace
```

Pin the Nighthawk image per campaign: `--set loadJob.image=ghcr.io/bpalermo/nighthawk:<sha>`.

## Running

```sh
# the whole ladder, R1..R8, unprofiled, into soak/results/<date>/
soak/ladder.sh
# one run
soak/ladder.sh soak/results/2026-09-xx rest-h2c:http2:realistic
# a single Job by hand
bazel run //charts:soak.upgrade -- --set loadJob.enabled=true,loadJob.target=grpc-jvm,loadJob.mode=grpc-unary,loadJob.tier=tiny,loadJob.runId=-r3
kubectl -n clj-grpc-soak logs -f job/nh-grpc-jvm-grpc-unary-tiny-r3 | soak/collect.sh grpc-unary
bazel run //charts:soak.upgrade -- --set loadJob.enabled=false
```

`ladder.sh` restarts the arm before every run (a tagged warmup step absorbs
the JIT), scales the sibling REST arm to zero, saves each Job's log, and
appends the collected table to `tables.md`. Any arm restart during a run
voids that run.

Ramps: unary tiny 200→2,400 req/s in 12 × 110 s steps (August's shape);
unary realistic 100→1,600; streams 400→4,800 msg/s at 20 streams and
4,000→16,000 at 40, as in August.

## Profiling

Every pod is already CPU-profiled by the cluster's OTel eBPF profiler, but a
JVM's JIT frames come out as hex. The JVM images carry Pyroscope's Java agent
jar, and `profiling.enabled=true` (`PROFILING=true soak/ladder.sh`) is what
loads it — the chart sets `JAVA_TOOL_OPTIONS=-javaagent:/pyroscope.jar` on
the `profile: true` arms, and nothing agent-related otherwise. That gate is
on the *load*, not the profiler, deliberately: an attached JVMTI agent turns
on the JVM's virtual-thread transition hooks on every mount and unmount even
while idle, which taxed the VT executor alone and confounded a VT-vs-direct
comparison (chart 0.2.8 fixed it; earlier JVM images loaded the agent in
their entrypoint). Series appear as `<arm>-java`, separate from the eBPF
`<arm>` series. The agent is a variable: run R3-tiny with and without before
trusting any profiled table, and never mix profiled and unprofiled rows in
one comparison. An A/B that sets `JAVA_TOOL_OPTIONS` itself through
`LADDER_EXTRA_SET` keeps its flags: on a profiled run the chart appends the
agent to them instead of emitting the variable twice.

## Runtime direct linking

The JVM arms run with `-Dclojure.compiler.direct-linking=true`, set by the
chart (`directLinking.enabled`, on by default) rather than baked into the
images, so a run can A/B it with `--set directLinking.enabled=false` and no
rebuild. It is worth 5–17% CPU per request here (2026-09-08 runs) and it is
the only lever that reaches the codec: clj-protobuf, Pedestal and jsonista
all publish to Clojars as source, so Clojure compiles them at load time in
the image, and load-time compilation is exactly what this property links.
rules_clj's build-time `direct_linking` attribute cannot touch them, and
refuses to try.

It changes semantics, not just speed. The property is process-wide and
applies to everything loaded from source, so a linked call site no longer
sees a later redefinition: `with-redefs`, mocking and REPL reloading stop
taking effect through one. That is right for a server image and wrong for a
REPL, and it is why this is a value you can turn off rather than a property
of the image. Nothing in this repo redefines at runtime.

The native arm never gets it: a native image has no Clojure compiler and
loads nothing from source, so the property would be a flag that does
nothing.

## Grading

From `tables.md` (per step: delivered/s, p50/p99/p999, knee/s, CPU ms/req,
throttled s, heap MB, RSS MB):

- **plateau** = the last step with knee/s below 0.1% of offered and no growth
  in throttled seconds
- latency at **matched load**: the highest offered rate every arm on the
  ladder sustains (tiny: 800 req/s is the REST arm's clean ceiling)
- **CPU per request** at matched load, from the cgroup delta — not from the
  offered rate
- any restart voids the run; warmup rows are marked and excluded

## Cross-check

`streamCheck.enabled=true` runs the Clojure stream driver (the August
instrument) against the stream rung with the same streams/in-flight, so the
new per-message numbers can be reconciled with the old:

```sh
bazel run //charts:soak.upgrade -- --set streamCheck.enabled=true,streamCheck.target=grpc-jvm
kubectl -n clj-grpc-soak logs -f job/stream-check
```
